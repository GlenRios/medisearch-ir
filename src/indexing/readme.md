# Module 2 — Indexing

## Overview

Module 2 builds the two search indexes that power the hybrid retrieval system. It reads the processed chunks produced by M1 and constructs a **BM25 lexical index** and an **HNSW dense vector index** in parallel. Both indexes are persisted to disk so that M3 can load them on demand without rebuilding.

## Files

### `embedder.py`

Handles loading the sentence-transformers model and generating dense vector embeddings for every chunk.

**Key functions:**

```python
load_model(model_name: str) -> SentenceTransformer
```

Loads the embedding model from HuggingFace and caches it for the lifetime of the process. The model is downloaded automatically on first use (~80 MB) and stored in the local HuggingFace cache. No API key is required — inference runs fully locally.

```python
generate_embeddings(
    texts: list[str],
    model: SentenceTransformer,
    batch_size: int = 64,
    show_progress: bool = True
) -> np.ndarray
```

Encodes a list of raw chunk texts into a float32 embedding matrix of shape `(N, D)`. Embeddings are **L2-normalized** before being returned, which allows cosine similarity to be computed as a plain inner product or, in the case of HNSW, derived directly from L2 distance.

**Default model:**

| Property | Value |
|---|---|
| Model | `sentence-transformers/all-MiniLM-L6-v2` |
| Embedding dimension | 384 |
| Download size | ~80 MB |
| Normalization | L2 (applied at generation time) |
| Inference | Local CPU (or CUDA if available) |

### `bm25_indexer.py`

Builds and persists the BM25 lexical index from the lemmatized token lists produced by M1.

**Key functions:**

```python
build_bm25(
    tokenized_corpus: list[list[str]],
    k1: float = 1.5,
    b: float  = 0.75
) -> BM25Okapi
```

Constructs a `BM25Okapi` index from the corpus token lists. Each entry in `tokenized_corpus` corresponds to the `tokens` field of one chunk.

**BM25 parameters:**

| Parameter | Default | Description |
|---|---|---|
| `k1` | `1.5` | Term frequency saturation. Controls how much repeated terms increase the score. Typical range: 1.2–2.0. |
| `b` | `0.75` | Length normalization. `0` = no normalization, `1` = full normalization. |

```python
save_bm25(index: BM25Okapi, output_path: Path) -> None
load_bm25(index_path: Path) -> BM25Okapi
```

Serialize and deserialize the index using `pickle`. The index is saved to `indexes/bm25.pkl`.

```python
build_chunk_map(chunks: list[dict]) -> dict
save_chunk_map(chunk_map: dict, output_path: Path) -> None
load_chunk_map(map_path: Path) -> dict
```

The chunk map is a dictionary that maps each `chunk_id` to its display metadata. It is used at retrieval time to convert a BM25 or FAISS result position back into human-readable information without having to reload the full chunks file.

**Chunk map entry:**

```json
{
  "wiki_00001_c003": {
    "text":     "The kidneys are responsible for long-term blood pressure...",
    "title":    "Hypertension",
    "url":      "https://en.wikipedia.org/wiki/Hypertension",
    "category": "Cardiology",
    "doc_id":   "wiki_00001"
  }
}
```

### `faiss_indexer.py`

Builds and persists the HNSW dense vector index from the embeddings generated by `embedder.py`.

**Index type — `IndexHNSWFlat`:**

HNSW (Hierarchical Navigable Small World) is a graph-based approximate nearest neighbor algorithm. Unlike `IndexFlatIP`, it does not perform exhaustive search — instead it navigates a multi-layer proximity graph to find near-optimal neighbors in sub-linear time.

| Property | Value |
|---|---|
| Index type | `faiss.IndexHNSWFlat` |
| Distance metric | L2 (Euclidean) |
| Search type | Approximate nearest neighbor (ANN) |
| Training required | No |
| Recall control | `ef_search` parameter |

**HNSW parameters:**

| Parameter | Default | Description |
|---|---|---|
| `M` | `32` | Number of neighbors each node connects to. Higher → better recall, more memory. Range: 16–64. |
| `ef_construction` | `200` | Candidate list size during build. Higher → better graph quality, slower build. Range: 100–400. |
| `ef_search` | `128` | Candidate list size during queries. Higher → better recall, slower queries. Can be changed at runtime. |

**Note on similarity scores:**

HNSW returns L2 distances, not similarity scores. Since embeddings are L2-normalized, the two are monotonically related. The `search_faiss()` function converts L2 distance to a cosine similarity score in `[0, 1]` using:

```
similarity = 1 - (l2_distance / 2)
```

This keeps scores consistent with the rest of the system (higher = more similar).

**Key functions:**

```python
build_faiss(
    embeddings: np.ndarray,
    m: int = 32,
    ef_construction: int = 200,
    ef_search: int = 128
) -> faiss.IndexHNSWFlat
```

```python
save_faiss(index, chunk_ids, index_path, ids_path) -> None
load_faiss(index_path, ids_path) -> tuple[faiss.IndexHNSWFlat, list[str]]
```

```python
search_faiss(
    index: faiss.IndexHNSWFlat,
    query_vector: np.ndarray,
    chunk_ids: list[str],
    top_k: int = 10
) -> list[tuple[str, float]]
```

The `chunk_ids` list is stored separately in `faiss_ids.json` because FAISS only understands integer positions — the list maps each integer position back to its `chunk_id` string.

## Output files

### `indexes/bm25.pkl`

Pickled `BM25Okapi` object. Contains the fitted inverse document frequency table and all term frequency vectors for the corpus.

### `indexes/faiss.index`

Binary HNSW index file written by `faiss.write_index()`. Contains the full graph structure and all stored vectors.

### `indexes/faiss_ids.json`

Ordered list of `chunk_id` strings. The integer position in this list corresponds to the integer position in the FAISS index.

```json
["wiki_00001_c000", "wiki_00001_c001", "wiki_00001_c002", ...]
```

### `indexes/chunk_map.json`

Flat dictionary mapping every `chunk_id` to its display metadata. Used by both retrievers in M3 to return human-readable results.

### `indexes/index_stats.json`

Build summary saved after each run. Example:

```json
{
  "total_chunks":      3812,
  "embedding_model":   "sentence-transformers/all-MiniLM-L6-v2",
  "embedding_dim":     384,
  "bm25_k1":           1.5,
  "bm25_b":            0.75,
  "bm25_build_secs":   4.2,
  "embed_build_secs":  187.5,
  "faiss_build_secs":  3.1,
  "faiss_index_type":  "IndexHNSWFlat"
}
```

## How to run

Make sure M1 has been executed and `data/processed/chunks.json` exists.

```bash
python -m src.indexing
```

On first run, `sentence-transformers` will download the embedding model from HuggingFace. An internet connection is only required for this initial download. All subsequent runs use the locally cached model.

Expected runtime on CPU (300 articles, ~3800 chunks):

| Step | Approximate time |
|---|---|
| BM25 build | 2–5 seconds |
| Embedding generation | 3–10 minutes |
| HNSW build | 2–5 seconds |

## Design decisions

**Why HNSW instead of IndexFlatIP?**
`IndexFlatIP` performs exhaustive exact search — every query vector is compared against every stored vector. For 3800 chunks this is fast enough, but HNSW provides sub-linear query time with negligible recall loss (>99% recall at `ef_search=128`), making it a better foundation as the corpus grows. It also requires no training step unlike `IndexIVFFlat`.

**Why L2-normalize embeddings before indexing?**
HNSW uses L2 distance internally. When vectors are L2-normalized (unit length), the L2 distance between two vectors is a monotonic function of their cosine similarity, so the ranking produced by HNSW is equivalent to cosine similarity ranking. This avoids needing a separate cosine index type.

**Why store `chunk_ids` separately from the FAISS index?**
FAISS is designed for numeric data and uses integer positions internally. String identifiers like `chunk_id` are stored externally in `faiss_ids.json`. The position in that list corresponds 1-to-1 with the position in the FAISS index, allowing results to be mapped back to their original chunk metadata.

**Why pickle BM25 instead of rebuilding on every query?**
Building BM25 from 3800 chunks takes a few seconds, but loading a pickled object takes milliseconds. Since the index is static once built, persisting it eliminates unnecessary computation on every retrieval session startup.
